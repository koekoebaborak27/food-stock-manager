## 2026-09-05 セッションの実装方法をハッシュ化トークン方式に決めた

`00_認証と家族グループ共通.md`で「詳細設計で決める」としていた保留事項。[`docs/specs/03_detail-design/10_認証と家族グループ/01_セッション設計.md`](../../specs/03_detail-design/10_認証と家族グループ/01_セッション設計.md)に決定を書いた。

- DBに`Session`テーブルを作り、Cookieには生トークン（32byteの乱数）だけを入れ、DBにはSHA-256ハッシュだけを持つ。DB漏えい時に生トークンを逆算できないようにするため
- `Session`は`User`と同じく家族グループの外側のテーブルとした。`01_データベース共通.md`3節の「家族グループの外にあるテーブルは`User`だけ」という記述はこの機能を実装するまで気づかれていなかった見落としで、`User`と`Session`に修正した

## 2026-09-05 Prisma7の破壊的変更でdatasource urlが使えず6系に落とした

`pnpm add -w -D prisma`で依存を足すと、`latest`タグが`8.0.0-rc.13`（RC）を指しており、まずこれを安定版`7.10.0`へ落とした。

ところが`7.10.0`で`prisma generate`すると次のエラーで失敗した。

```
Error: Prisma schema validation - (get-config wasm)
error: The datasource property `url` is no longer supported in schema files.
```

Prisma 7は`schema.prisma`の`datasource`ブロックに`url`を書く方式を廃止し、接続情報を`prisma.config.ts`側で持たせ、`PrismaClient`には`adapter`（ドライバアダプタ）を渡す方式に変わっていた。`prisma/AGENTS.md`が前提にしている「`schema.prisma`に`url = env("DATABASE_URL")`を書く」旧来の方式と食い違うため、最新の6系である`6.19.3`（`prisma` CLIと`@prisma/client`の両方）へ固定した。ドライバアダプタ方式への移行は、採用するとしても別途判断する。

## 2026-09-05 pnpmのpeerハッシュ不一致でPrisma Clientの生成物が見えなかった

`prisma`をルートのみの開発依存にし、`@prisma/client`をapps/apiにだけ入れた状態で`pnpm prisma:generate`を実行すると、コマンド自体は成功と表示されるのに、`apps/api`で`tsc`すると`Module '"@prisma/client"' has no exported member 'PrismaClient'`で失敗した。

原因は、pnpmが`@prisma/client`のpeer依存（`prisma`）の解決結果ごとに別々の内容アドレスハッシュでパッケージを複製すること。ルートから`prisma generate`を実行したときに書き込まれた生成物と、`apps/api/node_modules/@prisma/client`がシンボリックリンクで指す実体が、別ハッシュの複製になっていて一致していなかった。

`pnpm --filter api add -D prisma@6.19.3`で`apps/api`自身にも`prisma`を持たせたところ、`apps/api`側の`@prisma/client`が解決するpeerハッシュが生成先と一致し、解消した。**モノレポでは、`@prisma/client`を使うパッケージには`prisma`CLIも同じバージョンで入れておく**（ルートだけに置かない）。

## 2026-09-05 docker-composeのプロジェクト名衝突で他プロジェクトのDBボリュームを踏みかけた

`docker/docker-compose.yml`を新規作成し`docker compose -f docker/docker-compose.yml up -d db`で起動したところ、初回マイグレーション実行時にPrismaが「ドリフト検出」を報告し、`Contract` `Party` `News` `MasterCategory`など、このプロジェクトに存在しないテーブルを検出して`migrate reset`（全消去）を促してきた。

原因は、Docker Composeがプロジェクト名を明示しない場合に**compose.ymlを置いたディレクトリ名**（今回は`docker`）をプロジェクト名にすること。このマシン上の別プロジェクトも同じ`docker/docker-compose.yml`という配置を使っており、ボリューム名`docker_db-data`が衝突して、そちらの8日前のデータを持つボリュームをそのままマウントしてしまっていた。

`migrate reset`は実行せず（エージェント権限ポリシーでも禁止）、`docker compose down`でコンテナだけ止めて被害はなし。`docker-compose.yml`に`name: food-stock-manager`を明示し、`food-stock-manager_db-data`という専用ボリュームで作り直して解消した。**`docker-compose.yml`には必ず`name`を明示する**（ディレクトリ名が一般的な名前だと特に危険）。

## 2026-09-05 Nextjs16のproxy命名変更とAGENTSmd自動追記への対処

`apps/web/AGENTS.md`の記載どおり`src/proxy.ts`に`middleware`という名前でエクスポートしたところ、Next.js 16では`middleware`ではなく`proxy`という関数名でのエクスポートが必須になっており、起動時にエラーになった。関数名を`proxy`に直して解消。

また`next dev`起動時に`apps/web/AGENTS.md`の末尾へ、Next.js側が独自の注意書き（`<!-- BEGIN:nextjs-agent-rules -->`）を毎回自動追記する挙動に気づいた。このリポジトリの`AGENTS.md`はClaude/Codex/Copilot共通の正本であり、フレームワーク側に書き換えさせたくないため、`next.config.ts`に`agentRules: false`を設定して無効化した。
