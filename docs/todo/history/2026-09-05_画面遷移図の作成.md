## 2026-09-05 全体ナビゲーションを下部タブに決める

要件では「ヘッダーに世帯名・検索・メニュー」「右下にFAB」までしか決まっておらず、常備食リストと買い物リストの行き来の手段が未定だった。次の3案をモックで見比べて決めた。

| 案 | 内容 | 判断 |
| --- | --- | --- |
| 下部タブ2つ + ヘッダーメニュー | 採用 | 上部が保存区分タブだけで済み、片手操作の要件にも合う |
| 上部タブ | 不採用 | 「常備食／買い物リスト」と「すべて／冷蔵／冷凍／常温」でタブ行が2段になり、要件 4.1「フィルタを画面の上半分に積み上げないこと」に触れる。同じ高さでカードが1枚分減る |
| ヘッダーメニューのみ | 不採用 | 常備食と買い物リストの行き来が毎回2タップになる |

いったん「タブは上のほうがよい気がする」という意見が出たため、両案を並べたモックを提示したうえで下部タブに落ち着いた。**画面の絵を見せずに文章だけで決めようとすると判断が止まる**ので、レイアウトに関わる決めごとは先にモックを出す。

設定系（メンバー・通知・アカウント）はタブに出さず、ヘッダーのメニューに収めた。**このときは消費済リストもメニュー側に置いたが、同じ日にタブへ上げた**（後述）。

## 2026-09-05 一覧からの削除を追加する

要件では削除の入口が常備食の詳細画面だけ、買い物リストは購入済みの一括削除だけだった。一覧からも消したいという要望を受けて、要件定義書2件を変更した。

- [`20_常備食管理`](../../specs/01_requirements/20_常備食管理/01_常備食管理.md) の 4.1 と 4.8
- [`30_買い物リスト`](../../specs/01_requirements/30_買い物リスト/01_買い物リスト.md) に 4.4 を新設し、以降の節番号を繰り下げ

操作方法は次のとおり決めた。

| 論点 | 決定 | 理由 |
| --- | --- | --- |
| 削除の操作 | カードに常時表示するゴミ箱のアイコン | スワイプは気づかない人がいる。長押しはさらに気づかれにくく、操作に不慣れな家族が使う前提に合わない |
| ゴミ箱の位置 | 常備食は食品名と同じ行の右端、残数の増減は下段の右。買い物リストはチェックが左端・ゴミ箱が右端 | 増減ボタンやチェックとの押し間違いを避けるため、縦横に離す |
| アイコンの色 | 赤で塗らない | 全カードに赤が並ぶと一覧が騒がしい。赤は確認ダイアログの「削除する」だけに使う |
| 確認 | 一覧でも確認ダイアログを出す | 確認なしで消して「元に戻す」で救う案も出したが、詳細画面と扱いを揃える方を採用 |

確認ダイアログの文言には「食べ終えた場合は、削除ではなく残数を0にしてください」を入れた。削除は消費済リストに残らないため、消費済と取り違えると記録が消える。

## 2026-09-05 消費済リストをタブへ上げカートの導線を足す

消費済リストを常備食・買い物リストと同列に扱いたいという要望を受けて、下部タブを3つにした。ヘッダーのメニューに残るのはメンバー・通知の設定・アカウントの設定の3つ。

タブが3つになるとラベルの幅が足りないため、タブの表示は「常備食」「買い物」「消費済」と短くし、画面の見出しでは正式な名前を使うことにした。

あわせて、常備食リストのカードから買い物リストへ1タップで送れるようにした。それまでの経路は「詳細を開いて追加」か「残数を0にしてシートから追加」の2つで、**まだ残っているものを買い足したい場面が詳細経由の3タップ**になっていたため。カードの右上はカート・ゴミ箱の順に並べ、残数の増減はカードの下段に置いて離した。

スワイプで「買い物へ」「削除」を出す案は、ゴミ箱の常時表示をやめることになるため採らなかった。操作に不慣れな家族が使う前提では、見えているものを押せる形を優先する。

消費済リストからも買い物リストへ追加できるようにした（[`30_買い物リスト`](../../specs/01_requirements/30_買い物リスト/01_買い物リスト.md) の 4.2 で経路は5つ）。食べ切ったものをまた買う流れが、消費済リストを見ながら完結するため。消費済リストからは外さない。

画面名は「常備食一覧」から**「常備食リスト」**へ改めた。買い物リスト・消費済リストと呼び方をそろえるため。

図では、画面が移らない操作（削除・買い物リストへの追加）を**点線**で描き分けた。最初は図に描いていなかったが、一覧に削除があることが図から読み取れないという指摘を受けて足した。**画面遷移図には「画面が移らないが一覧から物が消える操作」も描かないと、読み手は削除の入口を見落とす。**

## 2026-09-05 用語を使い切りから消費済へ変える

「使い切り」を「消費済」に改めた。タブのラベルとして短く収まり、状態を表す言葉として読みやすいため。送り仮名なしの「消費済」を選んだ。

置き換えは要件定義書・基本設計書・図のソースに一括で適用した。対応は次のとおり。

| 旧 | 新 |
| --- | --- |
| 使い切り | 消費済 |
| 使い切り履歴 | 消費済リスト |
| 使い切った日付 | 消費済にした日付 |
| まだ使い切られていない | まだ消費済になっていない |

[2026-09-04 の記録](2026-09-04_要件定義の合意.md)は当時の言葉のまま残している。過去の記録を書き換えると、いつ何を決めたかが追えなくなるため。読むときはこの対応表で読み替える。

## 2026-09-05 図の作成で詰まった点

- mermaid の **subgraph のタイトルは折り返すと枠からはみ出して切れる**。ノードのラベルと違い枠の高さが伸びない。10文字程度に収めること。「下部タブで行き来する2画面」が「下部タブで行き来する2画」に切れて気づいた。
- 独立した subgraph を2つ置くと、宣言した順とは**逆に左右へ並ぶ**ことがある。`A ~~~ B` の見えない線でつなぐと縦に積まれ、狙った順になる。
- Docker Desktop が起動していないと `docker run` が `npipe:////./pipe/dockerDesktopLinuxEngine` の接続エラーで落ちる。`docker --version` は Docker Desktop が停止していても答えるため、起動確認には使えない。`docker info` を使う。
- 仕上がりの確認は [`docs/diagrams.md`](../../diagrams.md) のとおり PNG を一時出力して目視した。PNG はコミットしていない。
