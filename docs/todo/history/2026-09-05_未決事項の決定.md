## 2026-09-05 アクセス制御をバックエンドの実装だけに決める

旧・未決事項1。世帯をまたいだ参照を防ぐ仕組みを、データベース側の行レベルセキュリティに任せるか、バックエンドの実装で担保するか。

| 案 | 判断 | 理由 |
| --- | --- | --- |
| バックエンドの実装だけ | 採用 | 要件 6.2 で「フロントエンドからデータベースへ直接接続しない」と決めており、行レベルセキュリティの本来の利点（クライアントが直接つないだときの防御）が効く場面がない |
| 行レベルセキュリティだけ | 不採用 | Supabase 標準の認証ではなく Google ログインを自前で扱うため、行レベルセキュリティが前提とする「今の利用者は誰か」をデータベースへ渡す仕掛けを別に作る必要がある。テーブルを足すたびに規則を書く手間も続く |
| 両方を併用 | 不採用 | 漏洩耐性は最も高いが、初期版としては実装量が見合わない |

**採用の条件として、要件 6.2 に4つの決めごとを追記した。** 実装ミスがそのまま漏洩になる方式なので、仕組みで縛らないと成立しないため。

1. 世帯IDを検索条件へ加える処理を共通のデータ取得層1か所にまとめ、各機能が直接データベースを操作しない。
2. 世帯に属するデータを持つテーブルには必ず世帯IDの列を持たせる。
3. 他の世帯のデータが返らないことを機能ごとの自動テストで確かめる。IDを直接指定した場合も返さない。
4. 行レベルセキュリティに頼らないことを明記する。

3つ目の「IDを直接指定した場合も」は、一覧のAPIだけを試験して満足しないための歯止め。詳細取得・更新・削除は世帯の絞り込みを書き忘れやすい。

なお2の世帯ID列は、将来この判断を覆して行レベルセキュリティを足すときの前提にもなる。今回は使わないが、後戻りできる形は残しておく。

## 2026-09-05 通知の配信を単一のスケジューラに決める

旧・未決事項4。世帯ごとに通知時刻が違うため、誰がいつ配信処理を起動するかを決める必要があった。

| 案 | 判断 | 理由 |
| --- | --- | --- |
| Cloud Scheduler のジョブ1本を定期的に動かし、その時刻に該当する世帯だけ配信する | 採用 | 通知時刻の変更がデータベースの更新だけで完結する。世帯が増えても構成が変わらない |
| 世帯ごとにジョブを作る | 不採用 | 世帯を作るたび・時刻を変えるたびに外部サービスのジョブを操作することになり、その操作が失敗したときの整合が面倒。ジョブ数に応じた費用も増える |
| Cloud Tasks で次回分を予約し直す | 不採用 | 無駄な起動はないが、予約の取り消しと再予約が必要で実装が最も複雑 |

起動役を Cloud Scheduler 以外にする案も検討した。「無料枠が3ジョブまでで、他のアプリの分がなくなるのがもったいない」という懸念が出たため。

- **GitHub Actions の定期実行** — 定期実行の起動が混雑時に数分から十数分遅れると公式に明記されている。「8時15分に設定したのに8時35分に届く」ことが起きるため採らなかった。設定した時刻に届くことは通知機能の信頼に直結する。
- **Supabase の pg_cron** — 外部サービスが増えない利点はあるが、無料プランは一定期間アクセスがないとプロジェクトが一時停止する仕様があり、停止中に通知が止まるおそれがある。

費用の懸念については、Cloud Scheduler の課金対象は**ジョブの本数であり実行回数ではない**ため、4本目以降が有料になっても月あたり十数円の見込みだと説明して納得を得た。ただしこの数値は裏が取れていない（後述）。

あわせて要件 3.2 に「同じ世帯へ同じ日に2回以上配信しない」を追記した。定期実行が重なって動いた場合に2通届くのを防ぐため。実現方法（配信記録に世帯IDと配信日の重複禁止をかける等）は基本設計で決める。

## 2026-09-05 通知の刻みを15分に決める

定期実行の間隔が、そのまま利用者が選べる通知時刻の刻みになる。5分・15分・30分を比べて15分にした。

| 間隔 | 月の起動回数 | vCPU秒の見積り（1回5秒と仮定） | 無料枠180,000 vCPU秒に対して |
| --- | --- | --- | --- |
| 5分ごと | 約8,640回 | 約43,200秒 | 約24% |
| 15分ごと | 約2,880回 | 約14,400秒 | 約8% |
| 30分ごと | 約1,440回 | 約7,200秒 | 約4% |

5分ごとでも無料枠には収まるが、この枠はアプリ本体の利用でも消費するため余裕を残した。朝の通知が15分ずれても体験に差がなく、時刻の選択も「時」と「00 / 15 / 30 / 45」の2列で済んで片手で選びやすい。要件 3.3 に「選べる時刻を15分単位とすること」を追記した。

Cloud Run の無料枠（月200万リクエスト / 180,000 vCPU秒 / 360,000 GB秒、請求先アカウント単位）は[公式ページ](https://docs.cloud.google.com/free/docs/free-cloud-features)で確認済み。上表の vCPU 秒は1回の処理を5秒と仮定した見積りであり、実測ではない。

## 2026-09-05 配信手段をWeb Push標準に決める

| 案 | 判断 | 理由 |
| --- | --- | --- |
| ブラウザ標準の Web Push（VAPID鍵）を直接使う | 採用 | 外部サービスが増えず無料。要件のiOS案内とも噛み合う |
| Firebase Cloud Messaging を介す | 不採用 | ブラウザでは結局同じ Web Push の仕組みの上に乗るだけで、iOSの制約も変わらない。プロジェクト管理が増え、フロントに読み込む分だけ重くなる |
| 外部の通知サービス | 不採用 | 家族の購読情報を外部に預けることになり、保持する個人情報を最小限に保つ要件 6.5 と相性が悪い |

「ホーム画面に追加したPWAでも通知が届くのか」という確認があった。**通知を受け取るのは画面ではなくバックグラウンドで動く Service Worker** なので、アプリを閉じていても届く。むしろ iOS では逆に、iOS 16.4以降かつホーム画面へ追加した場合にしか届かない（Safari のタブでは通知の許可すら求められない）。この制約は要件 3.1 に既に書かれていたため、追記は不要だった。

次の2点は基本設計で扱う。要件へは書かず、ここに残す。

- iOS でホーム画面のアイコンを削除すると購読情報も消える。再度追加したら通知を有効にし直す案内が要る。
- 長期間アプリを開かないと購読が失効することがある。失効時の扱いは要件 5 の「購読情報が無効になっていた → 削除する」で足りている。

## 2026-09-05 検索対象を食品名だけに決める

旧・未決事項6。要件 4.2 は元から「食品名で絞り込めること」だったが、メモを含めるかが未決だった。食品名だけに確定させ、要件 4.2 へ「メモを検索の対象としないこと」を明記した。

決め手は使い勝手ではなく**表示との整合**。一覧のカードに出るのは食品名・保存区分・残数と単位・期限の状態・作り置きタグだけで、メモは詳細画面にしかない（要件 4.1 と 4.6）。メモを検索対象にすると、入力した言葉がどこにも見当たらないカードが結果に並び、利用者には理由が分からない。

納得できる形にするならカードにメモの一部を表示する必要があるが、それは「フィルタを画面の上半分に積み上げない」「余白を十分に取る」というデザイン方針と衝突する。切替スイッチで両立させる案も、片手操作前提の検索欄に操作を1段増やすため採らなかった。

将来拡張の候補（9節）へ「メモを含めた検索。一覧のカードにメモの一部を表示することとあわせて検討する」を8番目として足した。優先度は最下位。
