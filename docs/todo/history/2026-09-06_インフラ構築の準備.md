## 2026-09-06 Cloud Runの最小インスタンス数を0のままに決める

旧・未決事項1。[`01_プロダクト共通.md` 6.7節](../../specs/01_requirements/00_共通/01_プロダクト共通.md#67-コスト)がすでに「最小インスタンス数を0とすることを基本とする」と書いており、実質的にはその方針を最終決定として確定させただけ。

| 案 | 判断 | 理由 |
| --- | --- | --- |
| 最小インスタンス数0 | 採用 | 個人の学習目的で月額費用を最小に保つ（6.7節）ことが最優先。家庭内利用で24時間365日の稼働保証もしない（6.6節）ため、コールドスタートの数秒〜十数秒の待ちより無課金を優先できる |
| 最小インスタンス数1 | 不採用 | 常時起動分の課金が発生する。無料枠の範囲での運用（6.7節）という方針と合わない |

起動待ちが実際に使ってみて許容できないほど大きい場合は、6.7節に書いてあるとおり見直す余地を残す（今回は変更しない）。

## 2026-09-06 Supabaseのバックアップを無料プランの既定値に決める

旧・未決事項2。取得頻度・保持期間を個別に設定する案も検討したが、Supabase の無料プランでは変更できる項目がほぼ無く（有料プランでのみ選択可能）、決め直す余地がないと分かったため「既定値をそのまま使う」に決めた。

実際の頻度・保持期間の値は未確認。[`infra_design_01_事前準備.md`](../../specs/99_infra/infra_design_01_事前準備.md)でSupabaseプロジェクトを作成したあと、管理画面で確認して[`docs/todo/notes/`](../notes/README.md)へ実測値を残す（[`infra_design_06_今後の課題.md` 3節](../../specs/99_infra/infra_design_06_今後の課題.md#3-supabase-バックアップの実測値確認)に次のタスクとして記録済み）。

## 2026-09-06 デプロイ手順を7ファイルに分けて書いた

[`docs/specs/99_infra/`](../../specs/99_infra/README.md)配下に、概要・事前準備・Artifact Registry・Secret Manager・Cloud Run・Cloud Scheduler・今後の課題の7ファイルを作った。実際の値（プロジェクトID・接続文字列等）は書かず、すべてプレースホルダにしてある（[`README.md`](../../specs/99_infra/README.md)の書き方の注意に従った）。

デプロイの順序で守るべき制約が1つある。**web の Docker イメージは、ビルド時の引数 `API_BASE_URL` に api の Cloud Run URL を焼き込む**（[`apps/web/Dockerfile`](../../../apps/web/Dockerfile)。Next.js の `output: "standalone"` の仕様で実行時に変更しても反映されない）ため、**api を先にデプロイして URL を確定させてから web をビルドし直す**必要がある。同じ理由で Google OAuth のコールバック URL（`GOOGLE_CALLBACK_URL`）も、ブラウザが直接叩く api の URL ではなく **web の URL** を使う（`apps/web/next.config.ts` の rewrites が `/api/*` を api へ転送しているため、ブラウザは web の URL しか知らない）。

CI/CD の自動化（GitHub Actions から Cloud Run へ自動デプロイ）は、このタイミングでは行わないことにした。Workload Identity 連携の設定が手動デプロイ手順と重複するため、まず手動デプロイを一通り確認してから着手する方が手戻りが少ないと判断した（[`infra_design_06_今後の課題.md`](../../specs/99_infra/infra_design_06_今後の課題.md)）。コードの変更は発生しなかったため、ドキュメントのみの変更として`main`へ直接push可能（[`AGENTS.md`の最小規約](../../../AGENTS.md#最小規約)）。
