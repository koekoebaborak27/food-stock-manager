## 2026-09-05 食品名・メモの文字数上限を決めた

[共通の基本設計を決めたとき](2026-09-05_共通の基本設計.md)に保留にしていた、入力の文字数上限を決めた。

| 項目 | 決めた内容 | 理由 |
| --- | --- | --- |
| 食品名 | 30文字以内 | 家族グループ名（20文字）より長い実際の料理名（例:「鶏むね肉の生姜焼き用下味冷凍」)を入れられるようにしつつ、一覧のカード1行に収まる長さで打ち切る |
| メモ | 200文字以内 | 自由記述だが一覧には出さない項目のため、詳細画面で読み切れる長さに抑える |

## 2026-09-05 消費済とそのままにするをconsumedAtで区別する方式にした

要件4.7「残数を0にしたときの3択」を満たす方式の選択。

| 案 | 判断 | 理由 |
| --- | --- | --- |
| 削除と同じ`deletedAt`で消費済も表す | 不採用 | 「取り消す（削除）」と「消費済にする」は`01_データベース共通.md`の消し方一覧ですでに別の種類として分かれており、1列にまとめると一覧・消費済リストの絞り込み条件が複雑になる |
| `consumedAt`を新設し、nullで「常備食として表示中（そのままにする、を含む）」を表す | 採用 | 常備食リストは`consumedAt IS NULL`、消費済リストは`consumedAt IS NOT NULL`と条件が対称になり、「そのままにする」（残数0だが常備食のまま）も自然に表現できる |

## 2026-09-05 買い物リストへの追加はこの機能のAPIに含めないことにした

常備食リスト・詳細のカートアイコン、消費済リストからの追加はいずれも買い物リストへの書き込みだが、`ShoppingItem`の定義とAPIは30_買い物リストの設計が正本のため、20_常備食管理の`02_API.md`には経路を追加せず「30_買い物リストの処理を呼ぶ」とだけ書いた。30_買い物リストの基本設計で、常備食からの追加経路とその入力（商品名・元の`Stock`の`id`）を定める。

## 2026-09-05 並び替えは専用アイコンからのシートにした

要件4.3「並び替えの操作はメニューに収め、一覧の上部を占有しない」の実現方法の選択。

| 案 | 判断 | 理由 |
| --- | --- | --- |
| ヘッダーの三本線メニュー（メンバー・通知・アカウント設定と共通）に追加 | 不採用 | `00_画面共通.md`でこのメニューは家族グループ横断の3画面専用と決まっており、画面固有の並び替えを混ぜると意味が変わる |
| 検索アイコンの隣に並び替え専用アイコンを置き、下から出るシートで選ばせる | 採用 | 一覧の上部に並び替えの行を占有せずに済み、`00_画面共通.md 6.3`のシートの仕組みをそのまま使い回せる |

## 2026-09-05 買い物リストの設計を補完した

既存の未コミットの [買い物リスト設計](../../specs/02_basic-design/30_買い物リスト/README.md) を要件と照合し、画面・API・DB 更新・実際のエラー文言を補完した。

- 未購入へ戻す操作と削除の復元にも重複判定を適用し、未購入の商品名を一意に保つことにした。
- 購入状態と在庫更新をまとめて処理し、再送による二重加算を防ぐこと、残数上限で失敗した場合の案内を追加した。
- 一括削除は確認時の対象と更新日時を送る形にした。確認後に家族が購入した商品まで削除しないため。
- 元の食品が消費済みでも保存区分の初期値を引き継ぐよう、要件との不一致を修正した。
- 元の食品が残っている場合は、保存区分が同じなら残数を1増やし、異なれば新しく登録する方針をユーザーが承認した。選択を無視したり元の食品を別の保存区分へ移したりせず、購入した分だけを選んだ保存区分へ登録するため。要件・共通仕様・画面をそろえ、買い物リストの基本設計を完了した。
- README は基本設計の索引へ案内済みで、機能・起動方法の変更もないため、ルートの README と README_SIMPLE は更新しない。
