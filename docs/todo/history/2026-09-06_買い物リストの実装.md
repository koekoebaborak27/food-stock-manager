## 2026-09-06 スタックPRのbase branchが消えて自動クローズされた不具合

7e-1（PR #19）と7e-2（PR #20、PR #19からのスタックPR）は、7b（[積み上がったPRを順にmainへマージした](2026-09-05_アカウント設定の実装.md#2026-09-05-積み上がったprを順にmainへマージした)）と同じ「後続PRが前のPRのブランチから分岐する」パターンで作業していた。

- PR #19を`gh pr merge --squash --delete-branch`でマージした際、そのブランチ（`codex/shopping-list-schema-and-list-api`）を削除した
- PR #20のbaseがそのブランチだったため、GitHubがbase branch消失を検知してPR #20を**自動クローズ**した。`gh pr edit --base main`・`gh pr reopen`はどちらも「baseが存在しないクローズ済みPRは操作できない」という趣旨のエラーで失敗した
- **これは2026-09-05の7bマージ作業（[積み上がったPRを順にmainへマージした](2026-09-05_アカウント設定の実装.md#2026-09-05-積み上がったprを順にmainへマージした)）で一度発生し、「以後はまだ他のPRがbaseにしているブランチは削除しない」と教訓化されていた事象そのもの。今回`gh pr merge --squash --delete-branch`を実行する前にこの教訓を思い出せず、同じ手順を再度踏んでしまった**
- 復旧手順: ローカルの`codex/shopping-list-screen`（PR #20のheadブランチ）はリモートに残っていたため、`git rebase main`でmainの上に載せ替えた（7e-1の内容はすでにsquashでmainに入っているため、同一内容のコミットは自動的にスキップされた）。force-pushの権限が無かったため、書き換えたブランチは`codex/shopping-list-screen-v2`という別名で新規pushし、そこから改めてPR #21（base: main）を作成してマージした。PR #20はクローズ済みのまま経緯をコメントで残した
- **教訓（再掲）**: スタックPRの前段PRをマージするときは`--delete-branch`を付けない。後続PRがまだそのブランチをbaseにしている間は削除せず、後続PRのbaseを`main`へ付け替えてから（または後続PRもマージし終えてから）ブランチを消す。この教訓を次に忘れないよう、プロジェクトメモリ（`project-household-feature-stacked-prs`）にも明記した

## 2026-09-06 購入状態変更を実装した（7e-4）

[PR #23](https://github.com/koekoebaborak27/food-stock-manager/pull/23)としてmainへsquashマージ。このPRをbaseにした後続PRは無かったため、7e-1・7e-2で発生したスタックPR問題は今回も再発しなかった。

- `apps/api/src/shopping-item/validation.ts`に`validatePurchasedInput`を追加した。`isPurchased`が真偽値でない場合や`updatedAt`が日時として解釈できない場合は`VALIDATION_ERROR`、`isPurchased`・`returnToStock`・`storageType`の組み合わせが[`02_API.md`1節](../specs/02_basic-design/30_買い物リスト/02_API.md#1-経路の一覧)の条件を満たさない場合は`INVALID_PURCHASE_UPDATE`にする
- `ShoppingItemService.setPurchased`で`PATCH /api/shopping-items/{id}/purchased`を実装した。[`01_購入時の常備食反映.md`](../specs/03_detail-design/30_買い物リスト/01_購入時の常備食反映.md)の手順どおり、未購入→購入済みで`returnToStock: true`のときだけ`$transaction`の中で商品の条件付き`updateMany`（`isPurchased: false`・`updatedAt`一致）→常備食への反映を行う。常備食側は`stock.service.ts`の`adjustQuantity`と同じ「条件付き`updateMany`1回で判定と更新を同時に行う」方式で残数を+1し、`count === 0`のとき`id`・`householdId`だけで読み直して「3節の条件が崩れていた（新規作成に切り替え）」と「残数が99で上限到達（`SOURCE_STOCK_QUANTITY_LIMIT`を投げてロールバック）」を区別する。未購入に戻す（`isPurchased: false`）は商品だけの条件付き`updateMany`で完結させ、常備食は変更しない
- 商品の更新条件（`isPurchased`の現在値・`deletedAt`・`updatedAt`）を満たさない場合は、存在しない・別世帯・削除済み・購入状態の食い違い・`updatedAt`の食い違いを区別せず`SHOPPING_ITEM_UPDATE_CONFLICT`にまとめた（詳細設計1節が要求する「区別しない」方針どおり）
- 買い物リスト画面（`ShoppingListPage`）のチェック操作を有効化した。購入済みへ変更するときだけ購入確認シート（常備食へ戻すか・保存区分の選択、[`10_買い物リスト.md`4.1節](../specs/02_basic-design/30_買い物リスト/10_買い物リスト.md#41-購入確認シート)）を出し、未購入へ戻すのは確認なしで即時PATCHする。保存区分の初期値は元の常備食（`sourceStock`、未削除なら消費済でも使う）があればその保存区分、無ければ冷蔵にした
- 更新競合（`SHOPPING_ITEM_UPDATE_CONFLICT`）は、常備食詳細画面（`StockDetailPage`）と同じ「読み込み直す」のみのダイアログを表示し、閉じた際に購入確認シートも閉じて一覧を読み直す。残数上限到達（`SOURCE_STOCK_QUANTITY_LIMIT`）は購入確認シート内にエラー文言を表示し、入力を保持したまま「常備食へ戻さない」を選び直せるようにした
- DB統合テスト（`shopping-item.service.int.test.ts`の`setPurchased`）で、常備食への反映4分岐（新規作成・残数+1・保存区分の食い違いによる新規作成・消費済/削除済による新規作成）・残数上限到達時のロールバック（商品・常備食のどちらも変更されないこと）・更新競合を実DBで確認した。単体テスト（`validation.test.ts`）も追加
- `pnpm lint` / `format:check` / `typecheck` / `test`（365件）が通過。ブラウザでの実画面確認は環境にGoogle OAuthの認証情報が無いため未実施（7d-3以降と同様の制約）。未ログイン時に`/shopping-list`がログイン画面へリダイレクトされること・コンソールエラーが無いことのみ確認した

## 2026-09-06 削除・一括削除・復元を実装した（7e-5）

- `ShoppingItemService`に`remove`（`DELETE /api/shopping-items/{id}`）・`removePurchased`（`DELETE /api/shopping-items/purchased`）・`restore`（`POST /api/shopping-items/restore`）を追加した。[`02_重複判定と一括操作の整合性.md`3節](../specs/03_detail-design/30_買い物リスト/02_重複判定と一括操作の整合性.md#3-一括削除一括復元の全件一致確認)の手順どおり、一括操作は`$transaction`の中で「存在確認（`id`・`householdId`だけで絞る）」→「状態確認（購入済み/削除済み・`updatedAt`一致）」を分けて行い、存在しないIDがあれば404 `SHOPPING_ITEM_NOT_FOUND`、状態が食い違えば409 `SHOPPING_ITEM_UPDATE_CONFLICT`とし、全件一致のときだけ`updateMany`でまとめて更新する。1件削除も常備食詳細の`StockService.remove`と同じ「条件付き`updateMany`が0件なら存在確認だけで読み直して404/409を出し分ける」方式にした。応答はいずれも`{ items: [{ id, updatedAt }] }`とし、復元時にそのまま送り返せるようにした
- 買い物リスト画面（`ShoppingListPage`）のゴミ箱アイコン・削除確認ダイアログ（共通文言どおり「「〇〇」を削除しますか」）・購入済み一括削除ボタン（確認ダイアログに「対象：N件」を表示し、開いた時点の対象ID・`updatedAt`を確定させてから送信）・「元に戻す」帯（`showUndoToast`で5秒表示）を有効化した。購入状態変更で使っていた失敗処理（`handlePurchaseError`）を`handleActionError`へ改名し、削除・一括削除・復元でも共用した
- DB統合テスト（`shopping-item.service.int.test.ts`の`remove`・`removePurchased`・`restore`、17件追加）で、全件一致時の一括更新・1件でも競合/未購入/未削除でない場合の409・存在しない/別世帯IDの404・各操作を通じて対象外の行が変更されないことを実DBで確認した。単体テスト（`validateBulkItemsInput`、6件追加）も追加し、`pnpm lint` / `typecheck` / `test`（383件）が通過
- ブラウザでの実画面確認は、Google OAuthの代わりに`PrismaClient`で直接テスト用の`User`・`Household`・`Membership`・`Session`をDBへ作り、そのセッショントークンを`document.cookie`へ設定してログイン状態を再現する方法で実施できた（7d-3〜7e-4の「Google OAuthが無いため未実施」という制約を今回は回避）。1件削除→一覧から消える→「元に戻す」で復元、購入済み2件の一括削除→確認ダイアログに「対象：2件」→削除→「購入済みの商品を2件削除しました」の帯→「元に戻す」で復元、の一連の操作を確認した。作成した確認用データは作業後に削除した
