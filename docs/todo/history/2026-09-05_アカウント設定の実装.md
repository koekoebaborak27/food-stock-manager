## 2026-09-05 表示名変更と退会のAPIを実装した

`apps/api/src/users/`を新設し、`PATCH /api/users/me`と`DELETE /api/users/me`を追加した。退会は既存の`leaveCurrentHouseholdIfMember`を同じトランザクションから呼ぶため、管理者が他のメンバーを残す場合は既存どおり409 `HOUSEHOLD_HAS_OTHER_MEMBERS`で止まる。所属がなければ個人情報と全セッションを消し、`User`行は再ログイン時に再利用できるよう残す。DB統合テストで表示名の更新、一般メンバーの退会、管理者のブロック、所属なしの個人情報・セッション削除を確認した。

## 2026-09-05 アカウント設定画面を実装した

`apps/web/src/modules/account/`と`/settings`を追加した。アイコン・メールアドレス・表示名を表示し、表示名は既存の家族グループ名と同じ20文字上限・文言を共有する。保存成功時には「保存しました」の帯を出す。退会はブラウザからAPIを呼ぶため、APIが返すセッションCookie削除を受け取ってログイン画面へ戻れる。管理者が他のメンバーを残す場合は、実行ボタンを持たない退会不可ダイアログを表示する。既存の`LogoutButton`はこの画面に配置し、見た目だけ既存のボタン規約にそろえた。

## 2026-09-05 常備食の登録・編集を実装した

タスク7d-3として、`POST /api/stocks`・`PUT /api/stocks/{id}`と登録・編集画面を追加した。`GET /api/stocks/{id}`（編集画面が現在値と`updatedAt`を読むため）も合わせて実装した。残数の増減・削除・消費済・買い物リストへの追加は次のタスクへ送る。

- 入力チェックは項目ごとに`failedFields`へ集め、1件でも引っかかれば`VALIDATION_ERROR`の`details.fields`にまとめて返す（02_API共通.md「最初の1件で止めない」に対応）。保存区分は登録・編集画面が常に選択済みで開くため通常は起きないが、バックエンド側は要件定義どおり必須のまま持つ
- 登録時の重複名判定は、同じ家族グループ・未削除・未消費の範囲で食品名が完全一致するかだけを見る（部分一致にしない）。重複があっても登録は妨げず、応答の`duplicateName`で画面に伝える
- 編集の競合確認は`Stock.updateMany`の`where`に画面が読んだ`updatedAt`を含め、更新できた行数で判定する。0件のときだけ対象の有無を別途調べ、存在すれば`STOCK_UPDATE_CONFLICT`（409）、無ければ`STOCK_NOT_FOUND`（404）を返す。存在確認を先にしてから更新する二段階にしなかったのは、二人が同時に保存したときの競合を取りこぼさないため
- ついでに、一覧・詳細のAPI応答を組み立てる関数が`...stock`でPrismaの行を丸ごと展開しており、`householdId`など内部列まで応答に漏れていたのを直した。返す項目を明示的に列挙する形に直し、一覧用とメモを含む詳細用の2関数に分けた
- 画面は登録・編集で同じ`StockFormPage`を`mode`で出し分ける。保存区分・単位はピル選択、期限はネイティブの日付入力（カレンダー部品は未導入のため）。保存に成功すると常備食リスト画面へ戻り、その画面で結果の帯を出す必要があるため、文言は`sessionStorage`経由で1回だけ受け渡す（`save-toast.ts`）
- 編集時に`STOCK_UPDATE_CONFLICT`を受け取ったら、キャンセルのないダイアログ（「読み込み直す」のみ）を出し、押すと`GET /api/stocks/{id}`を呼び直してフォームと`updatedAt`を差し替える
- 常備食リスト画面のFABを`/stocks/new`へのリンクにした。編集画面へのリンクは、常備食の詳細画面（次のタスク）が無いため未着手
- バックエンドの入力チェック・DB統合テスト（1件取得・登録の重複判定・編集の競合と家族グループ絞り込み）、フロントエンドの入力チェック・保存結果の受け渡しを単体テストで追加した。ブラウザでの動作確認は、他セッションがポート3000/3001の開発サーバーを使用中だったことと、Googleログインが要ることから実施できていない
- `pnpm test`（297件）、`pnpm lint`、`pnpm typecheck`、`pnpm format` / `pnpm format:check`が成功した

## 2026-09-05 積み上がったPRを順にmainへマージした

PR #5→#6→タスク7c→#9→#10→#11 の5段スタックを、依存順に`main`へマージした。実装は終わっていたが、レビュー・マージ作業自体は行っていなかったため、今回まとめて片付けた。

- PR #5（タスク7bバックエンドAPI）をCI成功・コンフリクトなしを確認して`gh pr merge --squash --delete-branch`でマージした。
- **ここで想定外の事態が発生**: `--delete-branch`でリモートの`feat/household-management`を削除した直後、それをbaseにしていたPR #6が**GitHubの仕様で自動クローズ**された（コミット自体は`feat/household-screens`ブランチに残っていて消えていない）。base削除→自動クローズは、スタック構成のPRで`--delete-branch`を使うたびに起きる。以後は「まだ他のPRがbaseにしているブランチは削除しない」方針に切り替えた。
- 自動クローズされたPR #6は、同じ`feat/household-screens`から`main`を新しいbaseとして作り直し（PR #12）、マージした。
- 同様にPR #7（タスク7c、base: `feat/household-screens`）も、PR #12マージ時にbaseブランチが消えて自動クローズされたため、`codex/task-7c-account-settings`から`main`向けにPR #13として作り直した。ここで**base変更（`gh pr edit --base main`）を試したところ「Cannot change the base branch because the pull request is part of a stack」で失敗**した。GitHubがスタック関係にあるPRのbase変更を制限しているようで、この場合は新しいPRを作り直す以外に手段がなかった。
- PR #13は本物のコンフリクトを含んでいた（`README.md`の「状況」文言、`app.module.ts`のimports配列）。`codex/task-7c-account-settings`ブランチへ`git merge origin/main`でコンフリクトを解消し、両方とも内容を確認したうえで新しい方（HEAD側）を採用してから再度push・マージした。
- 以降のPR #9→#14、PR #10→#15も同じパターン（base変更失敗→新規PR作成→コンフリクト解消→マージ）で処理した。ダウンストリームPR（#10、#11）を自動クローズさせないため、マージ時は`--delete-branch`を付けず、baseにしているブランチが無くなった時点で改めて削除した。
- **もう1つ想定外だったこと**: PR #10→#15のマージ作業で、`git merge origin/main`の直前に`git fetch origin`をしていなかったため、**1つ前のPRがマージされる前の古い`main`を取り込んでしまった**。一度pushしてしまってから`gh pr view --json mergeable`が`CONFLICTING`のまま変わらないことで発覚し、`git fetch`→ 最新の`main`で`git merge origin/main`をやり直して解消した。以後、マージ作業のたびに直前で`git fetch origin`を徹底するよう改めた。
- 最後のPR #11（`codex/stock-register-edit`、タスク7d-3）は、スタックの末端だったからか`gh pr edit --base main`が成功した。「part of a stack」制限は中間のPRにだけかかり、末端PRには効かないと見られる。ただしここでもコンフリクト（`README.md`・`docs/todo/TODO.md`・stockモジュール一式のadd/add）が発生し、同様に解消してマージした。
- 全マージ完了後、重複した古いPR（#6・#7・#9・#10）をクローズし、マージ済みのブランチ（`feat/household-management`は#5マージ時に削除済み、残る`feat/household-screens`・`codex/task-7c-account-settings`・`codex/stock-list-api`・`codex/stock-list-page`）をリモート・ローカルとも削除した。最終的に残るブランチは`main`のみ。
- マージ後は毎回`pnpm test`・`pnpm lint`・`pnpm typecheck`・`pnpm format:check`を実行し、`main`最終状態でも297件成功を確認した。
