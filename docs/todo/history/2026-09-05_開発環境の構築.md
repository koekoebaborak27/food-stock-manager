## 2026-09-05 NextjsとNestjsをpnpm workspaceで別パッケージに分けた

当初は 1 つの `package.json` に両方の依存を入れる想定だったが、次の 2 点が両立しないことが分かった。

| 衝突点 | Next.js 側の要求 | NestJS 側の要求 |
| --- | --- | --- |
| モジュールの読み込み方式 | ESM でも CommonJS でも動く | 標準構成は CommonJS。`@Controller()` などの情報を実行時に読み取る仕組みが CommonJS 前提 |
| `tsconfig.json` の `noEmit` | `true`（ビルドは `next build` が行い、`tsc` は型検査だけ） | `false`（`tsc` が実際に `dist/` へ出力する） |

`noEmit` は同じファイルに真と偽を同時に書けないため、tsconfig の分割は避けられない。加えてルートの `package.json` には `"type": "module"` があり、NestJS を ESM で動かす道は設定が増えてはまりやすい。

| 案 | 判断 | 理由 |
| --- | --- | --- |
| 1 つの `package.json` に同居させ、tsconfig だけ分ける | 不採用 | `"type": "module"` と NestJS の衝突が残り、回避策を足し続けることになる |
| ルートから `"type": "module"` を外して CommonJS に統一する | 不採用 | `vitest.config.ts` など既存の ESM 前提の設定を巻き添えで直すことになる。Next.js 側に不要な制約を持ち込む |
| pnpm workspace で `apps/web` と `apps/api` に分ける | 採用 | `"type": "module"` を書くか書かないかをパッケージ単位で選べるようになり、衝突が根本から消える。tsconfig も各パッケージが `tsconfig.base.json` を読み込んで差分だけ上書きする形にできる |

## 2026-09-05 webをapps配下へ移す非対称な構成をいったん提案して取り下げた

workspace 化にあたり、最初は **`apps/api` だけを新設し、Next.js はルートに残す**非対称な構成を提案した。`src/` というパスがドキュメント 16 ファイル 36 箇所に書かれており、その書き換えを避けたかったため。

これはユーザーの「それはトレンドの構成か」という指摘で取り下げた。取り下げた理由は次のとおり。

- pnpm workspace / Turborepo / Nx いずれの標準例も `apps/` と `packages/` に分ける対称型で、**ルートの `package.json` はアプリを持たず束ね役に徹する**
- 非対称だとルートの `package.json` が「workspace の管理役」と「web アプリ本体」を兼ね、`pnpm build` がどちらの build なのか曖昧になる
- 将来 `apps/web` へ寄せるなら、**そのときも同じ 36 箇所を直す**ことになり、先送りの効果がない
- 実装がまだサンプル 1 ファイルしかない現時点が、移動コストが最も安い

実際に移動が必要だったファイルは 3 つ（`src/AGENTS.md` と `src/example/` の 2 ファイル）だけで、残りは文字列の置換で済んだ。**短期の手間を理由に標準から外れる判断は、規模が小さいうちほど割に合わない。**

## 2026-09-05 TypeScriptを最新の7系ではなく60系に固定した

NestJS 12 を入れた時点で `unmet peer typescript@>=6.0.0: found 5.9.3` が出た。TypeScript の最新は 7.0.2 だが、各パッケージの要求範囲を調べると交差点は 6.0 系しかなかった。

| パッケージ | TypeScript への要求 |
| --- | --- |
| `@nestjs/schematics` | `>=6.0.0` |
| `@nestjs/cli`（内部で同梱） | `~6.0.2` |
| `typescript-eslint` | `>=4.8.4 <6.1.0` |

7 系にすると `typescript-eslint` が対応範囲外になり `pnpm lint` が動かなくなる。**周辺ツールが直接読み込むライブラリは、最新版ではなく対応表の交差点を取る。**

あわせて、`pnpm add -D -w typescript@~6.0.3` と指定しても `package.json` には `^6.0.3` と記録される（pnpm の既定の記号が `^` のため）ことに気づき、手で `~6.0.3` へ直した。`^` のままだと将来 6.1 へ上がって `<6.1.0` の制約を外れる。

## 2026-09-05 Dockerfileの作成を後続タスクに回した

デプロイ先が Cloud Run のため Dockerfile は必ず要るが、今回は書かなかった。

- Dockerfile は「ローカルで通るビルド手順をコンテナ上で再現する」もの。再現すべき手順（`pnpm build`）が確定する前に書くと、遅くてエラーの読みにくい Docker のビルドの中でアプリのビルドエラーを潰すことになる
- workspace 構成では `node_modules` がリンクで張られるため単純な `COPY` では壊れ、`pnpm deploy --filter` で対象パッケージだけを取り出す手順が要る。**workspace の形が Dockerfile の書き方を決める**ので、構成の確定が先
- Cloud Run は `gcloud run deploy --source .` で Dockerfile なしでもデプロイできるが、workspace 構成では素直に効かないため、結局は書くことになる

先回りとして `apps/web/next.config.ts` に `output: "standalone"` だけ入れた。実行に必要なファイルだけを出力する設定で、コンテナへ `node_modules` を丸ごと入れずに済む。
