CIで一度失敗し同一コミットの再実行で成功していた`STOCK_UPDATE_CONFLICT`のDB統合テストを調査し、原因を直した。

## 2026-09-06 flakyの原因を特定した

`apps/api/src/stock/stock.service.int.test.ts`の`STOCK_UPDATE_CONFLICT`を確認するテスト（update・remove各1件）は、`prisma.stock.create()`直後の`updatedAt`を`staleUpdatedAt`として保持し、続けて`prisma.stock.update()`で書き換えたあと、古い`updatedAt`を渡した`service.update`/`service.remove`が競合エラーを返すことを期待していた。

`StockService.update`/`remove`は`where: { ..., updatedAt }`で楽観ロックの競合判定をしており（[stock.service.ts:117](../../../apps/api/src/stock/stock.service.ts:117)、[:204](../../../apps/api/src/stock/stock.service.ts:204)）、比較は完全一致。CIのように2回の書き込みが高速に連続すると、Postgresのタイムスタンプ精度内で`create`と`update`の`updatedAt`が同じ値に丸まり、`staleUpdatedAt`が実際の最新値と一致してしまうため競合が検出されず、更新が成功してテストが失敗していた。ローカルではDBの応答が遅く発生しにくいため再現しづらかった。

他のDB統合テストに同種の`updatedAt`依存が無いかリポジトリ全体を検索し、対象は本ファイルのみと確認した。

## 2026-09-06 テストを修正した

該当2箇所とも、2回目の`prisma.stock.update()`で`updatedAt`を`staleUpdatedAt`の1秒後へ明示的に指定するよう変更した。Prismaの`@updatedAt`は明示的に値を渡すとその値を使うため、DBの応答速度やタイムスタンプ精度に依存せず「先に更新されていた」状態を確実に再現できる。

検証: ローカルのDocker Postgres (`docker compose -f docker/docker-compose.yml up -d db`) に対し`stock.service.int.test.ts`を5回連続実行しすべて成功。`pnpm test`（全体, 321件）・`pnpm lint`・`pnpm typecheck`も成功。
