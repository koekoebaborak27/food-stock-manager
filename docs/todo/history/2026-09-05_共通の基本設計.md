## 2026-09-05 共通の基本設計を4ファイルに分けた

`02_basic-design/README.md` の書き方は「機能ごとにディレクトリを作る」だが、画面の枠・タグの表示・エラー文言・API の応答の形は 4 機能すべてで同じにする必要がある。どこか 1 機能の設計書に書くと、他の 3 機能から読みに行くことになり、書いた機能だけが太る。そこで機能の前に `00_共通/` を置き、次の 4 つに分けた。

| ファイル | 分けた理由 |
| --- | --- |
| `00_画面共通.md` | 画面を作るときにだけ読む |
| `01_データベース共通.md` | テーブルを足すときにだけ読む |
| `02_API共通.md` | 経路を足すときにだけ読む |
| `03_共通文言.md` | 単体テスト仕様書が文字列を写す先。文言を変えたときの差分をここだけに閉じる |

1 ファイルにまとめる案は不採用。20KB を超えて全文読みが必要になるうえ、文言の変更でファイル全体が動くため。

## 2026-09-05 他の家族グループのデータを404で返すことに決める

ID を直接指定して他の家族グループのデータを取ろうとしたときの返し方。

| 案 | 判断 | 理由 |
| --- | --- | --- |
| 404（見つからない） | 採用 | 403 だと「そのIDのデータは存在するが権限がない」ことが分かり、ID を総当たりすれば他の家庭のデータの有無を数えられる |
| 403（権限なし） | 不採用 | 上のとおり存在を漏らす。家庭内の利用とはいえ、要件 6.2 の「世帯をまたいだ参照は一切できない」に反する |

403 は「同じ家族グループの中で、一般メンバーが管理者だけの操作をした場合」にだけ使うことにした。

## 2026-09-05 画面に出す文言をフロントエンド側に持たせることに決める

API の失敗の応答に、画面へそのまま出す文言を含めるかどうか。

| 案 | 判断 | 理由 |
| --- | --- | --- |
| 種類を表す `code` だけ返し、文言はフロントエンドが選ぶ | 採用 | 文言の正本が `03_共通文言.md` の 1 か所に集まる。単体テスト仕様書もそこから写せる |
| バックエンドが文言も返す | 不採用 | 同じ意味の文言がバックエンドの実装と設計書の 2 か所に散る。文言を直すたびにバックエンドを直して出し直すことになる |

代わりに、知らない `code` が来たときの共通の文言を必ず用意することを決めた。バックエンドが先に新しい `code` を返しても、画面が空にならないようにするため。

## 2026-09-05 削除を行の削除ではなく印を付ける方式に決める

要件では「削除した食品はデータとしては残す」「削除直後に元に戻せる」と決まっている。これを満たす方式を決めた。

- `deletedAt` に日時を入れ、一覧の問い合わせで除く方式にした。元に戻すのは `deletedAt` を空にするだけで済む。
- 別のテーブルへ退避する案は不採用。戻すときに列を写し直す処理が要り、列を足すたびに 2 か所を直すことになるため。
- 招待コードと通知の送り先は行そのものを消すことにした。残しても使い道がなく、通知の送り先は個人情報にあたるため。

`deletedAt` の条件を付け忘れると削除済みが一覧に出る。世帯IDの条件と同じく、共通のデータ取得層 1 か所で付けることにした。

## 2026-09-05 日時をUTCで持ち日本時間で見せることに決める

期限の「今日」「明日」の判定が時間帯のずれで 1 日ずれると、期限切れの表示と通知が両方おかしくなる。次のとおり決めた。

- 保存は UTC、表示の直前に日本時間へ直す。
- 期限のように日付だけを持つ列は、時刻を持たない日付型にする。時刻付きで持つとずれの原因になるため。
- API での日付の受け渡しは `YYYY-MM-DD` の文字列にする。
- 「今日」の判定はバックエンドで行う。端末の時計と時間帯の設定を信用しない。

## 2026-09-05 保留にしたこと

- **セッションの持ち方**（Cookie の名前・有効期限・失効のさせ方）は 10_認証と家族グループ の設計で決める。共通側は「HttpOnly の Cookie で判定すること」までにとどめた。
- **呼びすぎを止める回数と時間**はインフラ構築時に決める。招待コードの照合とログインの入口にだけ制限を掛けることは決めた。
- **入力の文字数と数の上限の実際の値**は各機能の設計で決める。共通側は文言の形（「○文字以内で入力してください」）だけを決めた。
