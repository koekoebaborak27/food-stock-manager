## 2026-09-06 Prismaのマイグレーションに`DIRECT_URL`が必要と判明した

Supabaseの「Connect → ORM → Prisma」画面を確認したところ、`DATABASE_URL`（トランザクションプーラー、ポート6543）だけでは`prisma migrate deploy`が使えないと分かった。トランザクションプーラーはプリペアドステートメントに対応せずDDL実行に使えないため、マイグレーション専用に`DIRECT_URL`（セッションプーラー）を`schema.prisma`の`directUrl`へ追加する必要があった。

[PR #30](https://github.com/koekoebaborak27/food-stock-manager/pull/30)（`codex/supabase-direct-url`）で対応し、ユーザー承認のうえmainへマージした。

- `prisma/schema.prisma`に`directUrl = env("DIRECT_URL")`を追加
- `.env.example` / `.github/workflows/ci.yml`に`DIRECT_URL`を追加（ローカル・CIは`DATABASE_URL`と同じ値でよい）
- `docs/prisma_operations.md` / `prisma/AGENTS.md`の本番マイグレーション手順を2本立てに修正
- `docs/specs/99_infra/`のSecret Manager一覧・Cloud Runデプロイ手順を更新（本番データベースへのマイグレーション適用を新しい1節として追加）

ローカルの`.env`にも`DIRECT_URL`を追加してもらい、`pnpm typecheck` / `lint` / `format:check` / `test`（448件）で確認した。

## 2026-09-06 apiとwebをCloud Runへデプロイした

1. `pnpm exec prisma migrate deploy`をユーザーのPowerShellから実行し、Supabaseへ4件のマイグレーションを適用した。
2. `docker build` / `docker push`でapiイメージを作成・送信（エージェントが実行）。
3. `gcloud run deploy api`はユーザーが実行（本番Cloud Runサービスを差し替えるコマンドのため、権限ポリシーによりエージェントは単独実行しない）。Service URL: `https://api-450943687130.asia-northeast1.run.app`。
4. apiのURLを`API_BASE_URL`ビルド引数に使ってwebイメージを作成・送信。
5. `gcloud run deploy web`もユーザーが実行。Service URL: `https://web-450943687130.asia-northeast1.run.app`。
6. Google OAuthクライアントの「承認済みのリダイレクト URI」に本番のコールバックURLを追加し、`google-callback-url` / `web-base-url`シークレットを本番URLへ更新（`gcloud secrets versions add`）。
7. 新しいシークレットを反映するため`gcloud run services update api --update-secrets=...`を実行（`gcloud run services update`単体では「変更点なし」エラーになるため、`--update-secrets`で明示する必要があった）。

PowerShellでは`--set-secrets` `--update-secrets`のカンマ区切り値を引用符なしで渡すと壊れる、という落とし穴に複数回はまった（[落とし穴](../notes/インフラ構築.md)）。

## 2026-09-06 webの本番デプロイで500エラーが発生し、Dockerfileを修正した

Googleログイン自体は成功したが、トップページ（`/`）が500エラーになった。`gcloud run services logs read web`で確認したところ、`TypeError: fetch failed` / `ECONNREFUSED 127.0.0.1:3001`だった。

原因: `apps/web/Dockerfile`の`build`ステージで設定した`ENV API_BASE_URL`が`runtime`ステージに引き継がれていなかった。`next.config.ts`のrewrites（ブラウザからの`/api/*`転送）はビルド時に設定へ焼き込まれるため無事だったが、[`apps/web/src/shared/api/server-fetch.ts`](../../../apps/web/src/shared/api/server-fetch.ts)はサーバーコンポーネントの**実行時**に`process.env.API_BASE_URL`を直接読むコードで、こちらは実行用コンテナ側の環境変数が必要だった。存在しないため既定値の`http://localhost:3001`に接続しようとして失敗していた。

[PR #31](https://github.com/koekoebaborak27/food-stock-manager/pull/31)（`codex/web-runtime-api-base-url`）で`runtime`ステージにも同じ`ARG`/`ENV API_BASE_URL`を追加し、ユーザー承認のうえmainへマージ。`docker run --rm <image> printenv API_BASE_URL`で実行用イメージへ値が入ることを確認してから、webイメージを作り直して再デプロイした。
