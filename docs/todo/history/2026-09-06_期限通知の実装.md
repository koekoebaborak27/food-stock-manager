## 2026-09-06 スキーマと通知時刻APIを実装した（7f-1）

- `prisma/schema.prisma`に`PushSubscription`（`userId`一意、`householdId`を持たない。配信時は`User`→`Membership`をたどって世帯を判定する方針）と`NotificationSetting`（`householdId`一意、`notifyHour`既定8・`notifyMinute`既定0・`lastNotifiedOn`）を追加

- 単体テスト（`validation.test.ts`）と統合テスト（`notification-setting.service.int.test.ts`、世帯内の別利用者が変えても設定が共有されることを含む）を追加
- `pnpm lint` / `format:check` / `typecheck` / `test`（全体398件）が通過

### 詰まった点: `prisma migrate dev`が advisory lock 待ちで止まった

- `pnpm prisma:migrate -- --name <name>`で実行すると、`--`がpnpm経由で正しく渡らず対話プロンプトで止まる現象が発生した（過去のセッションでは問題なく通っていたが、今回はこの環境で再現）。バックグラウンド実行にしたまま停止させずにいたところ、Postgresのadvisory lock（`pg_advisory_lock`）を握ったまま残り、以降の`prisma migrate dev`が`P1002`（lock timeout）で失敗する状態になった
- `docker compose exec db psql -U app -d app_db`で`pg_stat_activity`を確認し、ロックを握ったまま`idle`になっているセッションを`pg_terminate_backend`で終了させることで復旧した
- 対処: `pnpm prisma:migrate --`ではなく`npx prisma migrate dev --name <name> < /dev/null`のように直接呼び出すと対話プロンプトを避けられる。マイグレーションが不自然に長く応答しない場合は、対話待ちを疑ってバックグラウンドタスクを止め、DBのadvisory lockが残っていないか`pg_stat_activity`で確認するとよい

- `pnpm lint` / `format:check` / `typecheck` / `test`（全体422件）が通過

### 詰まった点: Service Workerの登録が「リダイレクトされたスクリプト」として失敗した

- `apps/web/src/proxy.ts`の認証振り分け（未ログインならログイン画面へリダイレクト）のmatcherが`images`以外の静的ファイルを対象外にしていなかったため、`manifest.json` `sw.js` `icons/`配下が未ログイン時にすべて`/login`へ307リダイレクトされていた
- ブラウザの`navigator.serviceWorker.register("/sw.js")`はリダイレクトされた応答を仕様上許さないため、未ログインの画面（ログイン画面自体を含む）でService Workerの登録が常に失敗していた（コンソールに「The script resource is behind a redirect, which is disallowed.」と出る）
- 対処: `proxy.ts`の`matcher`に`manifest\\.json` `sw\\.js` `icons`を除外パターンとして追加し、ログイン状態に関わらずそのまま配信されるようにした。ブラウザで新しいタブを開いて`navigator.serviceWorker.getRegistrations()`を確認し、`activated`になることを確かめた

## 2026-09-06 配信バッチAPIを実装した（7f-4）

[PR #28](https://github.com/koekoebaborak27/food-stock-manager/pull/28)としてオープン（マージは未指示）。これでタスク7（機能を実装する）が完了。

- 先に[詳細設計: Web Push配信処理](../../specs/03_detail-design/40_期限通知/01_Web_Push配信処理.md)を書いた。基本設計（`00_期限通知共通.md`6節・`01_データベース.md`2節・`02_API.md`4節）が定める「条件付き更新1つで二重配信を防ぐ」を、`NotificationSetting`行がある世帯は`updateMany`の`count`判定、行が無い世帯（既定8:00・未配信）は`create`のユニーク制約違反（`P2002`）判定という2通りの排他制御に分けて設計した
- `apps/api/src/notification-dispatch/`にcontroller・service・moduleを追加し、`POST /api/internal/notifications/dispatch`を実装。認証は`SessionGuard`ではなく`InternalAuthGuard`（`X-Internal-Secret`ヘッダーと環境変数`INTERNAL_NOTIFICATION_SECRET`の一致だけを見る）
- `NotificationDispatchService.dispatch`は、現在時刻を日本時間の15分枠へ丸める純粋関数`toNotificationSlot`→対象世帯の確保（`claimHouseholds`）→世帯ごとに`StockService.countUrgent`（今回`StockModule`からexportして追加した新メソッド。既存の`urgentOnly`一覧絞り込みと同じ条件を再利用）で件数を数え0件ならスキップ→1件以上なら`notifyHousehold`で世帯に属する`PushSubscription`全件へ送信、という流れ
- 送信手段は`PushSender`インターフェース（`PUSH_SENDER`というDIトークン）で抽象化し、本番は`web-push`パッケージを呼ぶ`WebPushSender`、テストでは記録だけする偽実装に差し替えた。`WebPushSender`は`WebPushError`の`statusCode`が404/410のときだけ`invalid: true`を返し、呼び出し側が`deleteMany`でその購読を消す（それ以外の失敗は再送しない）
- 通知を押したときの遷移先（常備食リストの`urgentOnly=true`絞り込み）を実際に機能させるため、`apps/web`の`StockListPage`（トップ画面`/`）がこれまでURLの`urgentOnly`を読んでいなかった点を直した。`useSearchParams`で初期値を決めるようにし、`page.tsx`側を`<Suspense>`で包んだ
- 単体テスト（`notification-slot.test.ts`：15分枠への丸め方と日本時間の日付境界、`internal-auth.guard.test.ts`、`web-push-sender.test.ts`：`web-push`をモックし404/410だけ`invalid: true`になることを確認）と統合テスト（`notification-dispatch.service.int.test.ts`：枠の一致判定・二重配信防止・既定値世帯の扱い・0件時の非送信・複数利用者への配信・無効購読の削除。`stock.service.int.test.ts`に`countUrgent`のテストを追加）を実DBで実施
- `pnpm lint` / `format:check` / `typecheck` / `test`（全体448件）が通過。`pnpm --filter web build`は本タスクと無関係な既存の`server-only`インポートエラー（`main`ブランチの時点ですでに再現）で失敗することを確認済み。Googleログインを要する実画面（`urgentOnly=true`の絞り込み表示・実際のプッシュ受信）の動作確認は環境上未実施
