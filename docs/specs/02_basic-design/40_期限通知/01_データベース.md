# データベース

列の共通ルール（`id` `createdAt` `updatedAt`、家族グループでの切り分け、消し方、個人情報の消し方）は [01_データベース共通.md](../00_共通/01_データベース共通.md) のとおり。ここでは `PushSubscription` と `NotificationSetting` の列を定める。

## 1. PushSubscription

通知を送る先の端末（ブラウザの購読情報）。

| 列 | 型 | 決まり |
| --- | --- | --- |
| `userId` | UUID、一意 | `User` への外部キー。1 利用者につき 1 件 |
| `endpoint` | 文字列 | プッシュサービスのエンドポイント URL |
| `p256dh` | 文字列 | 購読の公開鍵 |
| `auth` | 文字列 | 購読の認証シークレット |

- **`householdId` を持たせない。** [01_データベース共通.md 3](../00_共通/01_データベース共通.md#3-家族グループでの切り分け)の対象からも外れている。配信時は `User` → `Membership` をたどって世帯を判定する。
- `userId` を一意にし、複数端末の同時購読は初期版では扱わない。別の端末でトグルをオンにした場合は、既存の行を新しい `endpoint` `p256dh` `auth` で置き換える（upsert）。
- 通知を受け取るかどうかの状態は、この行の有無で表す。専用の真偽値の列は持たない。トグルをオフにする操作は、この行を完全に消すことに対応する（[01_データベース共通.md 6](../00_共通/01_データベース共通.md#6-消し方)の「完全に消す」対象）。
- 配信に使ったところ購読情報が無効だった場合（プッシュサービスが 410 等で無効を伝えてきた場合）も、その行を完全に消す（[要件定義 5](../../01_requirements/40_期限通知/01_期限通知.md#5-例外時の扱い)）。
- 利用者が家族グループから脱退・退会したとき、家族グループそのものが削除されたときの扱いは [01_データベース共通.md 7](../00_共通/01_データベース共通.md#7-個人情報の消し方) と [10_認証と家族グループ/01_データベース.md 2](../10_認証と家族グループ/01_データベース.md#2-household) のとおり、この行も完全に消す。

## 2. NotificationSetting

家族グループ単位の通知時刻。

| 列 | 型 | 決まり |
| --- | --- | --- |
| `householdId` | UUID、一意 | `Household` への外部キー。1 世帯につき 1 件 |
| `notifyHour` | 整数（0〜23） | 通知を送る時刻の「時」。既定値 8 |
| `notifyMinute` | 整数（0 \| 15 \| 30 \| 45） | 通知を送る時刻の「分」。既定値 0 |
| `lastNotifiedOn` | 日付、null 許容（時刻を持たない） | 最後に配信した日（日本時間）。二重配信を防ぐために使う |

- 行が存在しない世帯は、時刻 8:00・未配信（`lastNotifiedOn` が `null` と同じ扱い）として扱う。世帯を作るたびに行を用意する処理は設けず、通知時刻を初めて変更したとき（`PATCH /api/notification-settings`）に upsert で行を作る。
- 配信バッチ（[02_API.md](02_API.md)）は、`notifyHour` `notifyMinute` が現在の日本時間の 15 分単位の枠と一致し、かつ `lastNotifiedOn` が今日（日本時間）でない世帯を対象にする。
- 二重配信の防止は、対象を検索する条件と `lastNotifiedOn` を今日に書き換える更新を 1 つの条件付き更新（`UPDATE ... WHERE householdId = ? AND (lastNotifiedOn IS NULL OR lastNotifiedOn <> 今日)`）にまとめて行う。配信処理が重ねて動いても、更新に成功するのは 1 回だけになり、後から実行した側は対象 0 件として何もしない。
- 通知本文をつくる件数の集計より先にこの更新を行い、更新できた世帯だけを配信対象として扱う。
