# API共通

フロントエンド（Next.js）とバックエンド（NestJS）のやり取りに共通する決まり。個々の経路と項目は各機能の設計書に書くこと。

## 1. 前提

- 画面はバックエンドの API だけを呼ぶこと。フロントエンドからデータベースへ直接つながないこと。
- API は JSON でやり取りすること。文字コードは UTF-8 とすること。
- 経路の先頭を `/api` にすること。例: `/api/stocks`。

## 2. 経路の付け方

| やること | 方法 | 経路の形 |
| --- | --- | --- |
| 一覧を取る | GET | `/api/stocks` |
| 1 件を取る | GET | `/api/stocks/{id}` |
| 作る | POST | `/api/stocks` |
| 全体を書き換える | PUT | `/api/stocks/{id}` |
| 一部だけ変える | PATCH | `/api/stocks/{id}/quantity` |
| 消す | DELETE | `/api/stocks/{id}` |

- 経路の名前は英語の複数形にすること。
- 絞り込み・並び替え・検索の条件は、GET の問い合わせ文字列で渡すこと。
- **家族グループの ID を経路にも本文にも入れさせないこと。** 誰の家族グループかはログイン状態から決めること。

## 3. 本人の特定

- ログインしているかどうかは、ブラウザから送られる HttpOnly の Cookie に入ったセッションで判定すること。Cookie の発行と失効の手順は 10_認証と家族グループ の設計書に書く。
- Google の ID トークンを、ログインの入口以外の API へ送らせないこと。
- ログインしていない場合は 401 を返すこと。フロントエンドは 401 を受け取ったらログイン画面へ移すこと。

## 4. 家族グループでの絞り込み

- リクエストから家族グループの ID を受け取らないこと。受け取っても使わないこと。
- ログインしている利用者が属する家族グループの ID を、毎回セッションから引くこと。
- データベースへの問い合わせに家族グループの条件を付ける処理は、共通のデータ取得層 1 か所にまとめること。各機能が生の問い合わせを組み立てないこと。
- ID を直接指定して他の家族グループのデータを取ろうとした場合は、403 ではなく **404** を返すこと。そのデータが存在すること自体を知らせないため。
- 他の家族グループのデータが返らないことを、機能ごとの自動テストで必ず確かめること。

## 5. 応答の形

### 5.1 うまくいったとき

- 一覧は `{ "items": [...] }` の形で返すこと。配列だけを返さないこと。後から件数などを足せるようにするため。
- 1 件を返すときは、その中身をそのまま返すこと。
- 作成は 201、変更は 200、削除は 204 を返すこと。204 のときは本文を返さないこと。

### 5.2 失敗したとき

失敗の応答は必ず次の形にすること。

```json
{
  "error": {
    "code": "STOCK_UPDATE_CONFLICT",
    "details": { "field": "name" }
  }
}
```

| 項目 | 決まり |
| --- | --- |
| `code` | 失敗の種類。英大文字とアンダースコアで書くこと |
| `details` | 補足。入力チェックの失敗では、どの項目かを入れること。無い場合は省略すること |

- **画面に出す文言を応答に入れないこと。** フロントエンドが `code` から文言を選ぶこと。文言の正本は [03_共通文言.md](03_共通文言.md) と各機能の設計書とすること。
- 知らない `code` を受け取った場合、フロントエンドは共通の失敗の文言を出すこと。

## 6. 状態コードと失敗の種類

| 状態コード | `code` | どんなとき |
| --- | --- | --- |
| 400 | `VALIDATION_ERROR` | 入力チェックに引っかかった |
| 401 | `UNAUTHENTICATED` | ログインしていない、またはセッションが切れた |
| 403 | `FORBIDDEN` | ログインはしているが、その操作をする権限がない |
| 403 | `NO_HOUSEHOLD` | どの家族グループにも属していない |
| 404 | `NOT_FOUND` | 見つからない。他の家族グループのデータを指した場合も含む |
| 409 | `CONFLICT` | すでに同じものがある、または先に更新されていた |
| 429 | `TOO_MANY_REQUESTS` | 短い時間に呼びすぎた |
| 500 | `SERVER_ERROR` | 上のどれでもない失敗 |

- 機能ごとに細かく分けたい場合は、`STOCK_UPDATE_CONFLICT` のように接頭辞を付けた `code` を足すこと。状態コードは上の表に合わせること。
- 入力チェックの失敗は、最初の 1 件で止めず、引っかかった項目をすべて `details` に入れて返すこと。

## 7. 値の受け渡し

| 種類 | 形 | 例 |
| --- | --- | --- |
| 日付（期限など） | `YYYY-MM-DD` の文字列 | `2026-09-05` |
| 日時 | 協定世界時の ISO 8601 文字列 | `2026-09-05T08:30:00.000Z` |
| ID | UUID の文字列 | `018f...` |
| 未設定 | `null` | 期限なしは `null` とすること |

- 日付に時刻を付けて送らないこと。時間帯のずれで日付が 1 日ずれるため。
- 「今日」の判定はバックエンド側で日本時間として行うこと。端末の時計を信用しないこと。

## 8. 更新の競合の伝え方

- 更新と削除の要求には、画面が読んだときの `updatedAt` を本文に入れさせること。
- 値が食い違う場合は保存せず、409 と競合を表す `code` を返すこと。
- 残数の増減はこの確認をしないこと。増減は差分として送らせること（[01_データベース共通.md](01_データベース共通.md)）。

## 9. 呼びすぎへの備え

- 招待コードの照合とログインの入口は、同じ利用者・同じ接続元からの呼び出しが短時間に続いた場合に 429 を返すこと。回数と時間はインフラ構築時に決めること。
- ほかの API に回数の制限は設けないこと。

## 10. ログ

- 失敗した要求は、経路・状態コード・`code`・利用者の ID・家族グループの ID をログに出すこと。
- **メールアドレス・表示名・食品名・商品名・メモ・セッションの中身・招待コードをログに出さないこと。**
- うまくいった要求は、経路と処理時間だけを出すこと。本文を出さないこと。
