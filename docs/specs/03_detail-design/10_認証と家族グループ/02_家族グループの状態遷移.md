# 家族グループの状態遷移

[00_認証と家族グループ共通.md](../../02_basic-design/10_認証と家族グループ/00_認証と家族グループ共通.md)・[01_データベース.md](../../02_basic-design/10_認証と家族グループ/01_データベース.md)・[02_API.md](../../02_basic-design/10_認証と家族グループ/02_API.md) だけでは分岐の全体像が追いにくい、脱退・除名・削除・招待コード参加の状態遷移をここにまとめる。

## 1. 「利用者を家族グループから外す」共通処理

脱退・除名・家族グループ削除・招待コードでの参加（切り替え）・退会のどれも、最終的には「ある利用者を今の家族グループから外す」処理を含む。この処理を1か所にまとめ、他の分岐から呼び出す。退会（`DELETE /api/users/me`）も `leaveCurrentHouseholdIfMember` を再利用するため、管理者が他のメンバーを残す場合は同じ409 `HOUSEHOLD_HAS_OTHER_MEMBERS` を返す。

1. 対象利用者の `Membership` 行を削除する。
2. 対象利用者の `User.displayName` `User.email` `User.avatarUrl` を空にする（[01_データベース共通.md 7節](../../02_basic-design/00_共通/01_データベース共通.md#7-個人情報の消し方)）。次にログインすれば入れ直される。
3. 対象利用者が発行した有効な `Invitation` があれば削除する（[01_データベース.md 4節](../../02_basic-design/10_認証と家族グループ/01_データベース.md#4-invitation)）。

## 2. 自己脱退（`DELETE /api/households/me/membership`）

| 呼び出した利用者 | 他のメンバー | 結果 |
| --- | --- | --- |
| 一般メンバー | いる／いない どちらでも | 1節の共通処理のみ実行する。家族グループは残す |
| 管理者 | いる | 何もせず 409 `HOUSEHOLD_HAS_OTHER_MEMBERS` を返す |
| 管理者 | いない（自分1人） | 1節の共通処理を実行したうえで `Household` 行も削除する。`Membership` `Invitation` は外部キーの `onDelete: Cascade` で自動的に消えるが、1節の3を先に行うため実質的な二重処理にはならない |

## 3. 除名（`DELETE /api/households/me/members/{userId}`）

| 呼び出した利用者 | 対象 | 結果 |
| --- | --- | --- |
| 一般メンバー | 誰でも | 403 `LAST_ADMIN_CANNOT_BE_REMOVED`（[02_API.md](../../02_basic-design/10_認証と家族グループ/02_API.md) の定義どおり。一般的な `FORBIDDEN` ではなくこの機能専用の `code` を使う） |
| 管理者 | 自分自身（`userId` が呼び出した利用者と同じ） | 403 `LAST_ADMIN_CANNOT_BE_REMOVED`（管理者は除名の経路で自分を外せない。脱退させたい場合は2節の脱退APIを使わせる） |
| 管理者 | 他の一般メンバー | 1節の共通処理を実行する |
| 管理者 | 存在しない `userId`、または他の家族グループの利用者 | 404 `NOT_FOUND` |

## 4. 家族グループの削除（`DELETE /api/households/me`）

| 呼び出した利用者 | 結果 |
| --- | --- |
| 一般メンバー | 403 `LAST_ADMIN_CANNOT_BE_REMOVED` |
| 管理者 | 家族グループに属する全メンバーへ1節の共通処理の2・3（個人情報のクリアと招待コードの削除）を行ったうえで `Household` 行を削除する。`Membership` は `onDelete: Cascade` で自動的に消える |

- 全メンバーの個人情報をクリアする理由: 家族グループが無くなればその利用者の `Membership` も無くなる点は脱退・除名と同じであるため、[01_データベース共通.md 7節](../../02_basic-design/00_共通/01_データベース共通.md#7-個人情報の消し方) の扱いをここでも揃える。共通データベース設計書はこの節で「`User` は消さないこと」とだけ明記しており、個人情報のクリアを禁じているわけではない。

## 5. 招待コードで参加するときの切り替え（`POST /api/invitations/redeem`）

1. 招待コードを `Invitation.code` で探す。無ければ404 `INVITATION_NOT_FOUND`、期限切れなら404 `INVITATION_EXPIRED`。
2. 呼び出した利用者が**その招待コードの家族グループにすでに所属している**場合（自分が発行した自分の家族グループのコードを自分で使った場合など）は、3・4を飛ばしてコードの削除だけ行う。脱退→再参加の処理を挟むと、管理者が自分1人だけの家族グループを一度削除したうえで、その消えたIDへ参加させようとして失敗するため。
3. それ以外で、呼び出した利用者がすでに何らかの家族グループに所属している場合、参加の前に**2節の自己脱退と同じ分岐**を行う。管理者かつ他のメンバーがいる場合は、参加を中断して409 `HOUSEHOLD_HAS_OTHER_MEMBERS` を返す。
4. 新しい家族グループへ一般メンバーとして `Membership` を作る。
5. 参加に使った `Invitation` 行を削除する（使い回し防止。[01_データベース.md 4節](../../02_basic-design/10_認証と家族グループ/01_データベース.md#4-invitation)）。

**判断の根拠**: 1人が同時に所属できる家族グループは1つ（`Membership.userId` が一意）であり、参加は必ず「今の家族グループを抜けてから入る」処理になる。抜けるときの制約を緩めると、他のメンバーが残る家族グループが管理者不在のまま残ってしまうため、既存の脱退ルールをそのまま適用する。

[13_招待コードで参加する.md](../../02_basic-design/10_認証と家族グループ/13_招待コードで参加する.md) にはこの分岐のエラー文言が明記されていない（管理者が確認ダイアログを経てここに到達すること自体まれなケースのため）。この場合は画面共通の失敗の帯文言「うまくいきませんでした。もう一度お試しください。」（[03_共通文言.md 2節](../../02_basic-design/00_共通/03_共通文言.md#2-通信と読み込みの失敗)）で受ける。

## 6. 招待コードの発行・再表示（`POST /api/invitations`）

1. 呼び出した利用者が発行した `Invitation` を探す（`createdById` が一意なので最大1件）。
2. 見つかり、かつ `expiresAt` が現在時刻より未来なら、その行をそのまま返す（コードと有効期限）。
3. 見つからない、または期限切れの場合は、期限切れの行があれば削除してから新しい行を作る（`code` を新規生成、`expiresAt` は発行時刻の7日後）。

### コードの生成方法

- セッションの生トークン（[01_セッション設計.md](01_セッション設計.md)）と同じ考え方で、暗号論的に安全な乱数から作る。総当たりされにくいよう十分な長さを確保する。
- 画面側は形式チェックをせずコピー＆貼り付けを前提とするため（[13_招待コードで参加する.md](../../02_basic-design/10_認証と家族グループ/13_招待コードで参加する.md)）、人が手入力しやすい短さは優先しない。
- 実装: `randomBytes(18).toString("base64url")` （URLに安全な文字だけ、24文字）。
