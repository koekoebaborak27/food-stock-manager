# セッション設計

[00_認証と家族グループ共通.md](../../02_basic-design/10_認証と家族グループ/00_認証と家族グループ共通.md) 2節で「詳細設計で決める」としていた、セッションIDから利用者を引く実装方法を定める。

## 1. 持ち方

DBに`Session`テーブルを作り、そこで管理する。

| 列 | 型 | 決まり |
| --- | --- | --- |
| `id` | UUID | 主キー |
| `userId` | UUID | `User`への外部キー |
| `tokenHash` | 文字列 | Cookieに入れる生トークンをSHA-256でハッシュ化した値。一意 |
| `expiresAt` | 日時 | 有効期限。発行・延長のたびに「今+30日」を入れ直す |
| `createdAt` `updatedAt` | 日時 | 共通列どおり |

- **Cookie（名前`session`）には生トークンだけを入れ、DBにはそのハッシュだけを持つ。** DBの中身が漏れても、ハッシュから生トークンを逆算してなりすませないようにするため。
- 生トークンは暗号論的に安全な乱数（32バイト、Base64URLなどURLに安全な文字だけの形）で作る。
- `Session`は`User`と同じく**家族グループの外側**にあるテーブルとする（[01_データベース共通.md](../../02_basic-design/00_共通/01_データベース共通.md) 3節を参照。ログインの仕組みであり、家族グループが持つデータではないため）。
- `Session`の行は完全に消す方式とする（[01_データベース共通.md](../../02_basic-design/00_共通/01_データベース共通.md) 6節の「完全に消す」に分類）。ログアウト・退会・有効期限切れの掃除で行ごと消す。

## 2. 発行（ログイン成功時）

1. `User`をGoogleアカウントの識別子で探す・無ければ作る・空行なら埋め直す（[01_データベース.md](../../02_basic-design/10_認証と家族グループ/01_データベース.md) 1節のとおり）。
2. 生トークンを作り、そのハッシュと`userId`、`expiresAt`（今+30日）で`Session`の行を作る。
3. Cookie `session`（`HttpOnly` `Secure` `SameSite=Lax`、有効期限30日）に生トークンを入れて返す。

## 3. 検証（APIリクエストのたび）

1. Cookieから生トークンを取り出す。無ければ未ログイン扱い（401 `UNAUTHENTICATED`）。
2. 生トークンをハッシュ化し、`Session`を`tokenHash`で探す。見つからない、または`expiresAt`が過去なら未ログイン扱い（見つかった場合は行を消す）。
3. 見つかった場合、`expiresAt`を「今+30日」へ延長して保存し、`userId`から`Membership`を引いて所属する家族グループと役割を求める。

## 4. 失効

- ログアウト・退会: 呼ばれた時点のセッションの`Session`行を消し、Cookieも消す。
- 有効期限切れ: 検証の際に見つかった期限切れの行はその場で消す（バッチ処理は設けない。行数が少ないため）。
