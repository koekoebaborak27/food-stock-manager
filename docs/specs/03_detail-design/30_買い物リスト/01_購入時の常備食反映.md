# 購入時の常備食反映

[00_買い物リスト共通.md 3節](../../02_basic-design/30_買い物リスト/00_買い物リスト共通.md#3-購入状態と常備食への登録)が定める4分岐の判定条件と、`ShoppingItem`・`Stock`という2つのテーブルを1つの処理として整合させる実装方法を、コードを読むだけでは追いにくい部分としてここにまとめる。対象は`PATCH /api/shopping-items/{id}/purchased`で`isPurchased: true`・`returnToStock: true`を受けた場合のみ。`returnToStock: false`や`isPurchased: false`（未購入に戻す）は`ShoppingItem`だけの更新で、[02_API.md](../../02_basic-design/30_買い物リスト/02_API.md)のとおり素直に実装できるため対象外。

## 1. 全体の流れ

1つのPrismaトランザクションの中で、次の順に行う。**途中でエラーを投げた場合はトランザクション全体を失敗させ、`ShoppingItem`・`Stock`のどちらも変更を残さない。**

1. `ShoppingItem`を条件付き`updateMany`で更新する。

   ```
   updateMany({
     where: { id, householdId, deletedAt: null, isPurchased: false, updatedAt: 送られてきた値 },
     data: { isPurchased: true, updatedById },
   })
   ```

   `count === 0`なら、対象が無い・別世帯・すでに削除済み・すでに購入済み・`updatedAt`が食い違うのいずれかであり、区別せず409 `SHOPPING_ITEM_UPDATE_CONFLICT`にする（[02_API.md](../../02_basic-design/30_買い物リスト/02_API.md)が要求する「現在と同じ購入状態を要求した」場合もこれに含む）。存在しない場合の404との切り分けは行わない。共通文言側は「読み込み直す」ダイアログを出すだけで404と409を区別して表示しないため、実装を複雑にしてまで区別する意味がない。
2. `sourceStockId`が無ければ、2節の「新規作成」を行い終了する。
3. `sourceStockId`があれば、`findFirst({ id: sourceStockId, householdId, deletedAt: null })`で元の常備食を読む（同じトランザクション内。`deletedAt`だけで絞り、`consumedAt`や保存区分では絞らない。分岐に使うため状態はそのまま受け取る）。
4. 3節の分岐に従って「残数+1」か「新規作成」かを決めて実行する。

## 2. 新規作成（分岐条件を満たさない・`sourceStockId`が無い場合）

```
stock.create({
  householdId, name: 商品名（sourceStockIdがあれば元の常備食のname）,
  storageType: 送られてきた値, quantity: 1, unit: null, expiresOn: null,
  isHomemade: false, memo: null, consumedAt: null, deletedAt: null,
  createdById: userId, updatedById: userId,
})
```

`createdById`・`updatedById`は購入操作をした利用者にする（元の常備食の登録者は引き継がない。[00_買い物リスト共通.md 3節](../../02_basic-design/30_買い物リスト/00_買い物リスト共通.md#3-購入状態と常備食への登録)）。元の`Stock`（あれば）はここでは一切更新しない。

## 3. 「残数+1」に進めるかどうかの判定

1節3で読んだ`sourceStock`について、次の**すべて**を満たす場合だけ残数+1へ進む。1つでも欠ければ2節の新規作成に切り替える。

| 条件 | 満たさない場合の扱い |
| --- | --- |
| `sourceStock`が見つかった（`findFirst`が`null`を返さない） | 新規作成（見つからない＝削除済み・存在しない） |
| `sourceStock.consumedAt === null`（未消費） | 新規作成 |
| `sourceStock.storageType === 送られてきたstorageType` | 新規作成（元は変更しない） |

判定用に読んだ`sourceStock`の値をそのまま使い、実行の直前に読み直さない。次節の条件付き`updateMany`が同じ条件をもう一度確認するため、判定後に他の利用者が元の常備食を変更していても二重更新にはならない。

## 4. 残数+1の実行と上限判定

条件をすべて満たす場合、次の条件付き`updateMany`を実行する（[stock.service.ts](../../../../apps/api/src/stock/stock.service.ts)の`adjustQuantity`と同じ、1回のSQLで判定と更新を同時に行う方式）。

```
updateMany({
  where: {
    id: sourceStockId, householdId, deletedAt: null, consumedAt: null,
    storageType: 送られてきた値, quantity: { lt: 99 },
  },
  data: { quantity: { increment: 1 }, updatedById },
})
```

- `count === 1`: 成功。1節の`ShoppingItem`更新とあわせてコミットする。
- `count === 0`: 3節の判定後に状態が変わった場合（同時に別の操作で削除・消費済・保存区分変更された場合）と、残数が99で上限に達している場合の2通りがある。区別するため、`id`と`householdId`だけで`sourceStock`を読み直す。
  - 見つからない、または`deletedAt`・`consumedAt`・`storageType`が3節の条件を満たさなくなっている → 2節の新規作成に切り替える（[00_買い物リスト共通.md 3節](../../02_basic-design/30_買い物リスト/00_買い物リスト共通.md#3-購入状態と常備食への登録)「利用者が選択して送った保存区分を優先し、異なれば新規作成する」のとおり、処理時点の最新の値で判定し直してよい）。
  - それ以外（条件は満たすが`quantity === 99`） → 409 `SOURCE_STOCK_QUANTITY_LIMIT`を投げてトランザクション全体を失敗させる。1節の`ShoppingItem`更新も巻き戻り、商品・常備食のどちらも変更されない。

同じ常備食へ複数人が同時に「残数+1」しても、上記の条件付き`updateMany`は1つのSQL文で判定と更新を行うため、行ロックの範囲内で競合が直列化され、100件目の加算だけが失敗する（99を超えて増えることはない）。事前に残数を読んでからJavaScript側で `+1` して書き込むような、読み取りと書き込みが別ステップになる実装は行わない。
