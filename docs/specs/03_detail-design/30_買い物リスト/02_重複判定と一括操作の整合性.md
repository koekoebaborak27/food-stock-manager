# 重複判定と一括操作の整合性

[00_買い物リスト共通.md](../../02_basic-design/30_買い物リスト/00_買い物リスト共通.md)・[01_データベース.md](../../02_basic-design/30_買い物リスト/01_データベース.md)・[02_API.md](../../02_basic-design/30_買い物リスト/02_API.md)が定める「同時実行でも壊れない」という要件を、実際にどのSQL・どの順で満たすかをここにまとめる。

## 1. 部分一意索引の作り方

[01_データベース.md 3節](../../02_basic-design/30_買い物リスト/01_データベース.md)が定める一意制約（`householdId`・前後空白を除いた`name`・`isPurchased = false`・`deletedAt IS NULL`）は、条件付き（部分）一意索引でなければ表現できない。Prismaの`schema.prisma`は`@@unique`にWHERE条件を書けないため、次の手順で作る。

1. `schema.prisma`の`ShoppingItem`には通常の列定義と`@@index([householdId, deletedAt, isPurchased, name])`（一覧・重複確認用、[01_データベース.md 2節](../../02_basic-design/30_買い物リスト/01_データベース.md)）だけを書く。一意制約は書かない。
2. `pnpm prisma migrate dev --create-only`でマイグレーションの雛形だけ作り、生成されたSQLに次の1文を手で足す。

   ```sql
   CREATE UNIQUE INDEX "ShoppingItem_household_name_unpurchased_key"
     ON "ShoppingItem" ("householdId", "name")
     WHERE "isPurchased" = false AND "deletedAt" IS NULL;
   ```

3. `name`は保存前に前後の空白を除いた値にしてから書き込むため、索引側でトリムする必要はない。大文字・小文字は区別する（[00_買い物リスト共通.md 2節](../../02_basic-design/30_買い物リスト/00_買い物リスト共通.md#2-商品の追加と重複)）ため、索引の照合順序は既定のままでよい。

## 2. 追加・未購入への変更・復元での重複検知

事前に`findFirst`で重複を確認してから`create`／`update`するだけでは、2つの処理が確認と書き込みの間に入れ違うと重複を防げない（確認したときは無かったが、書き込む直前にもう1件できている）。そのため次の二段構えにする。

1. まず`findFirst({ householdId, name, isPurchased: false, deletedAt: null }})`で重複を確認する。多くの場合はここで弾け、無駄なDBエラーを避けられる。
2. 確認を通っても、実際の`create`（追加・復元）または`update`（未購入へ戻す）は1節の一意索引に守られたまま実行する。索引違反（Prismaの`PrismaClientKnownRequestError`、`code === "P2002"`）を捕まえたら、1節で確認済みでも409 `SHOPPING_ITEM_ALREADY_EXISTS`に変換する。

この2番目のcatchが実質的な排他制御であり、1番目の事前確認は応答を速くするための最適化に過ぎない。**catchを省略しない。**

## 3. 一括削除・一括復元の全件一致確認

[02_API.md](../../02_basic-design/30_買い物リスト/02_API.md)は「対象の一部でも更新・削除済みなら全件を変更しない」ことを要求する。`id`ごとに`updatedAt`が異なるため、`updateMany({ where: { id: { in: ids }, updatedAt: ... } })`のような一括条件では書けない。次の順で1つのトランザクション内に行う。

1. 渡された`items`（`{ id, updatedAt }`の配列）を`id`の配列にし、`findMany({ where: { id: { in: ids }, householdId } })`で対象を**存在確認だけ**のため読む（`deletedAt`・`isPurchased`・`updatedAt`では絞らない）。
2. `ids`のうち1件でも2の結果に含まれなければ、404 `SHOPPING_ITEM_NOT_FOUND`で中断する（存在しない、または別世帯）。
3. 全件見つかった場合、それぞれの実物と依頼内容を比較する。
   - 一括削除: `isPurchased === true && deletedAt === null && updatedAt`が依頼の値と一致、を全件満たすか確認する。
   - 復元: `deletedAt !== null && updatedAt`が依頼の値（削除後の`updatedAt`）と一致、を全件満たすか確認する。
   - 1件でも満たさなければ、409 `SHOPPING_ITEM_UPDATE_CONFLICT`で中断する（復元にも同じ`code`を使う。[02_API.md](../../02_basic-design/30_買い物リスト/02_API.md)に復元専用の`code`は無く、基本設計もエラー文言を分けていないため）。
4. 全件が条件を満たす場合だけ、`updateMany({ where: { id: { in: ids }, householdId }, data: { deletedAt: 今 } })`（削除）または`updateMany({ where: { id: { in: ids }, householdId }, data: { deletedAt: null } })`（復元）を実行する。2〜3で確認済みのため`in`だけの条件でよい。

2（存在確認）と3（状態確認）を分けて判定する理由は、404と409を正しく出し分けるため。1回のクエリで「条件を満たすもの」だけを絞ると、存在しないのか競合なのかを区別できなくなる。
