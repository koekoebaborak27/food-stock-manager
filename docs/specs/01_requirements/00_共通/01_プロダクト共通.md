# プロダクト共通要件

## 1. 目的

家庭内の作り置き料理と食品ストックを家族で共有し、**食べ忘れと重複購入を減らす**こと。

達成できている状態を次のとおり定義する。

- 家族の誰もが、家にある食品と残数をスマホから即座に確認できること。
- 期限が近い食品と期限切れの食品に、一覧を開いた時点で気づけること。
- 切らした食品が、その場で買い物リストへ載ること。
- 買ってきた食品が、手入力をやり直すことなく常備食へ戻ること。

## 2. 対象ユーザー

同じ家に住む家族（世帯）。中心となる利用者は日々の買い物と食事の支度を担う家族と、その同居家族。

前提として扱うこと。

- スマホでの利用を主とすること。PCでの利用は動作すればよい程度とし、最適化しないこと。
- 家族には、アプリの操作に不慣れな人と子どもが含まれること。専門用語を使わず、入力項目を増やさないこと。
- 家族の人数は数名規模とすること。大人数の組織利用は想定しないこと。

## 3. 用語

| 用語 | 意味 |
| --- | --- |
| 常備食 | 本アプリが管理する食品の総称。作り置き料理と購入品の両方を含む。 |
| 作り置き | 家で作って数日かけて食べる料理。店で買った惣菜は含まない。 |
| 保存区分 | 食品の保存場所。冷蔵・冷凍・常温の3種。 |
| 残数 | その食品が今いくつ残っているか。整数。 |
| 単位 | 残数の数え方。個・袋・パック・食分・本・ごとの6種。 |
| 期限 | その食品をいつまでに食べるか。賞味期限と消費期限は区別しない。 |
| 消費済 | 残数が0になり、一覧から外れた状態。データは残る。 |
| 世帯 | 常備食と買い物リストを共有する家族のまとまり。家族グループとも呼ぶ。 |
| 管理者 | 世帯を作成した利用者。メンバーの除名と世帯の削除ができる。 |
| 招待コード | 世帯へ参加するために使う文字列。 |

利用者に見せる文言では「世帯」ではなく「家族グループ」を使うこと。

## 5. 権限

権限は世帯単位で決まる。世帯をまたいだ参照は一切できないこと。

| 操作 | 一般メンバー | 管理者 |
| --- | --- | --- |
| 常備食の登録・編集・削除・残数の増減 | できる | できる |
| 買い物リストの追加・チェック・削除 | できる | できる |
| 消費済リストの閲覧・再登録 | できる | できる |
| 招待コードの発行 | できる | できる |
| 通知時刻の変更 | できる | できる |
| 自分がその世帯から脱退する | できる | できる |
| 他のメンバーを除名する | できない | できる |
| 世帯を削除する | できない | できる |

- 管理者は世帯の作成者が自動的に就任すること。管理者は世帯につき1名とすること。
- 管理者の譲渡は初期版では提供しないこと。

## 6. 非機能要件

### 6.1 実行環境

| 項目 | 内容 |
| --- | --- |
| フロントエンド | Next.js + TypeScript |
| バックエンド | NestJS + TypeScript |
| 実行基盤 | Google Cloud Run |
| データベース | Supabase PostgreSQL |
| 認証 | Googleログイン |
| クライアント | スマホ中心のPWA |

### 6.2 認証とアクセス制御

- Googleログイン以外の認証手段を提供しないこと。パスワードを本アプリで保持しないこと。
- すべてのAPIは、ログイン中の利用者が所属する世帯のデータだけを返すこと。世帯IDをリクエストから受け取って信用しないこと。
- フロントエンドからデータベースへ直接接続しないこと。必ずバックエンドを経由すること。

### 6.3 通信とオフライン

- データの読み書きにはインターネット接続を必須とすること。
- 通信できない状態では「インターネットへの接続が必要です」と表示し、操作をさせないこと。
- PWAとして端末に保存するのは、画面の外枠・アイコン・スタイルまでとすること。食品データと買い物リストを端末に保存しないこと。
- ホーム画面へ追加でき、アプリのように全画面で起動できること。

### 6.4 性能

- 一覧画面は、通常の携帯回線で操作してから内容が表示されるまで3秒以内を目標とすること。
- 1世帯あたりの常備食は数百件までを想定すること。それを超える件数の最適化は初期版では行わないこと。

### 6.5 個人情報の保護

- 保持する個人情報は、Googleアカウントの表示名・メールアドレス・アイコンURLに限ること。
- 退会または世帯からの脱退が行われたとき、その利用者の表示名・メールアドレス・アイコンURLを削除すること。
- 食品と買い物リストは世帯に属するものとして残し、作成者の表示を「退会したメンバー」に置き換えること。
- 削除した食品・消費済にした食品はデータとしては残すこと。ただしそこにも個人情報を残さないこと。

### 6.6 可用性・バックアップ・運用

- 家庭内での利用を前提とし、24時間365日の稼働保証は行わないこと。
- データベースのバックアップはSupabaseの標準機能で取得すること。取得頻度と保持期間は構築時に決めること。
- 障害の切り分けができる程度のログをバックエンドに出すこと。ログに個人情報と認証情報を出さないこと。

### 6.7 コスト

- 個人の学習目的であり、月額費用を最小に保つこと。
- Cloud Runの最小インスタンス数を0とし、利用がない時間帯に費用が発生しない構成を基本とすること。起動待ちが体験を損なう場合に見直すこと。
- Supabaseは無料枠の範囲での運用を基本とすること。

### 6.8 アクセシビリティ

- 期限の状態を色だけで表さないこと。色・文言・アイコンの3つで表すこと。
- 文字と背景のコントラストを十分に確保すること。
- 主要な操作は片手で届く位置に置くこと。

## 7. デザインの方針

- スマホファーストとし、片手で操作できること。
- 背景はアイボリーから暖色系、文字は濃いブラウン系、主操作色はコーラルオレンジ系、枠線と未選択要素は淡いベージュ系とすること。
- カード・ボタン・入力欄には大きな角丸を使うこと。
- カード間と情報間の余白を十分に取ること。
- 見出しと食品名は太く大きく表示すること。
- 保存区分・期限状態・作り置きはピル型タグで表すこと。
- アイコンはシンプルな線画で統一すること。
- 一覧画面の右下に丸い追加ボタン（FAB）を置くこと。
- ログイン画面は、食卓・キッチン・家族を連想する写真の上に、濃色の大きな角丸パネルを重ねる構成とすること。

## 8. 初期版に含めないこと

| 項目 | 扱い |
| --- | --- |
| 食品の写真の撮影・添付 | 将来拡張 |
| オフラインでの閲覧・編集 | 提供しない |
| リアルタイム同期 | 将来拡張 |
| 食品ごとのコメント | 提供しない |
| 担当者の割り当て・非登録メンバー | 提供しない |
| 賞味期限と消費期限の区別 | 提供しない |
| 1人が複数の世帯に所属すること | 将来拡張 |
| 管理者の譲渡・複数管理者 | 将来拡張 |
| 削除した食品の履歴と復元 | 提供しない（削除直後の取り消しのみ提供する） |
| 残数の小数入力 | 提供しない |
| 期限の時刻指定 | 提供しない |
| PC向けの画面最適化 | 提供しない |

## 9. 将来拡張の候補

優先度の高い順に記す。

1. 期限入力のクイックボタン（+3日 / +1週間 / +1ヶ月）。
2. 消費済リストからの傾向表示（よく買う食品、消費ペース）。
3. 食品の写真。
4. 買い物リストのリアルタイム同期。
5. 招待リンク方式の追加。
6. 複数世帯への所属と切り替え。
7. 管理者の譲渡。
